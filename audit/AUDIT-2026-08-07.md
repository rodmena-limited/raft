# Mission-critical audit — raft-py

**Date:** 2026-08-07
**Subject:** `raft-py` @ `516441b`, intended to back `consensus.rodmena.co.uk`
**Ticket:** issuedb #1 · **Spec:** `SPECS/1-raft-mission-critical-audit.md`
**Harness:** `audit/evaluations/run_all.sh` — 11 probes, all reproducing live

## Bottom line

Eleven safety, durability, availability and security claims were tested against
a running cluster through its own gRPC interface. **All eleven were violated.**
Ten of the eleven are reproduced live and are marked CONFIRMED.

The baseline that made this necessary: `pytest` reports **134 passed, 96.45%
coverage**, and the coverage gate is green. Every defect below is present in
code that the suite covers. This is the dominant failure mode — the tests share
the implementation's mental model, so they cannot fail on the things the
implementation gets wrong.

**Harness honesty check.** Before treating a FAIL as a finding, the minimal fix
for Finding 1 was applied to `src/raft/core/state.py` and `probe_01` was shown
to flip to PASS; the patch was then reverted and the probe was confirmed to FAIL
again. The probes discriminate — they are not vacuously red. Source is unmodified
by this audit.

## CONFIRMED findings, ranked by customer harm

### 1. Every restart silently discards all committed state — CRITICAL
`src/raft/core/state.py:55-66`, `:131-136` · `probe_01_restart_replay.py`

`last_applied` is persisted to disk, but the state machine is in-memory and is
only ever rehydrated from a snapshot. `apply_entries()` replays from
`last_applied + 1`, so after a restart every entry at or below the persisted
`last_applied` is treated as already applied and is **never re-applied**.
Snapshots would normally cover this — but see Finding 10: nothing in `src/` ever
calls `maybe_snapshot()`, so no snapshot ever exists. The result is that *all*
committed data is lost on *every* restart.

This needs no crash. Observed on a clean, graceful shutdown:

```
pre-restart:  commit_index=1 last_applied=1 store={'account-42': b'balance-1000'}
post-restart: commit_index=1 last_applied=1 store={}
post-restart durable log holds 1 entries (indices [1]) -- the data IS on disk
VIOL acknowledged write is readable after restart (got None, expected b'balance-1000')
```

The data is intact on disk the whole time; the node simply refuses to replay it.
Nothing surfaces an error — the node reports itself as fully caught up.

**Smallest correct fix:** treat the state machine as volatile. On startup set
`last_applied` to the snapshot's `last_included_index` (0 if no snapshot) and
replay the log up to `commit_index`. Persisting `last_applied` is only safe if
the state machine is itself durable and committed atomically with the metadata.

### 2. A 32-byte anonymous request permanently wedges the cluster — CRITICAL
`src/raft/core/state.py:131-136`, `src/raft/sm/kv.py:21` · `probe_09_poison_entry_wedges_apply.py`

`apply_entries()` calls `sm.apply()` with no error handling, and the KV state
machine raises `ValueError` on an unrecognised op. The raising entry is already
committed and replicated, so every node re-reads it from `last_applied + 1` on
every subsequent apply and raises again. `last_applied` can never advance past
it — on any node, ever.

```
last_applied per node:              [1, 1, 1]
submitting an anonymous 32-byte payload with an unknown op
ClientWrite -> accepted=True index=2
after poison, last_applied:         [1, 1, 1]
after poison, commit_index:         [2, 2, 2]
post-poison ClientWrite -> accepted=True index=3
nodes holding the post-poison value: []
final last_applied per node:        [1, 1, 1]
```

Note what the cluster does *after* being poisoned: it keeps electing, keeps
accepting writes, keeps returning `accepted=True`, and keeps advancing
`commit_index` — while applying nothing, forever. It is bricked and reports
itself healthy. One unauthenticated request, no privileges, permanent.

**Smallest correct fix:** a command that fails to apply is a *committed* command
and must not be retried forever. Catch the exception in `apply_entries()`, record
the failure as that command's result, advance `last_applied` past it, and surface
it on a health signal. Application-level validation belongs before the entry
enters the log, not after it is committed.

### 3. Unauthenticated remote code execution — CRITICAL
`src/raft/sm/kv.py:13`, `src/raft/node/service.py:66,73` · `probe_07_unauthenticated_rce.py`

`KeyValueStateMachine.apply()` calls `pickle.loads()` on the command payload,
and that payload arrives directly from the network via `ClientWrite`. `pickle`
is a code-execution format by design. The transport offers no defence:
`add_insecure_port()` and `insecure_channel()` mean no TLS, no peer
authentication and no client authorisation anywhere in the codebase.

A client presenting no credentials of any kind caused code to run on the node:

```
node listening on 127.0.0.1:28591 (add_insecure_port: no TLS, no authentication)
marker file exists before the write? False
marker file exists after the write?  True
marker contents: 'code executed via unpickling of a network payload'
```

The payload used was benign (it wrote a marker file into the probe's own temp
directory). The severity comes from the reach: the payload is a **replicated log
entry**, so every follower unpickles it too. One anonymous request executes on
every node in the cluster. The same gadget also reaches `InstallSnapshot`, whose
snapshot blob is unpickled on restore.

**Smallest correct fix:** three independent changes, all required. Replace
`pickle` with a non-executing codec (protobuf/JSON/CBOR) for both command
payloads and on-disk state; put mTLS on the peer transport via
`add_secure_port`/`secure_channel`; and require client authorisation on
`ClientWrite`. Do not expose this port to any untrusted network in the meantime.

### 4. One unresponsive peer makes the cluster permanently leaderless — CRITICAL
`src/raft/core/logic.py:138`, `:204` · `probe_05_slow_peer_stalls_leader.py`

`maybe_start_election()` does `await asyncio.gather(*(ask_peer(p) for p in
peers))` and **no gRPC call anywhere in the codebase carries a timeout or
deadline**. A peer that is reachable but wedged — GC pause, disk stall, deadlock,
network blackhole — never returns, so the gather never completes and the votes
are never counted. `broadcast_append_entries()` has the identical structure, so a
wedged peer also stops the leader heartbeating everyone else.

Against a 3-member cluster with a healthy 2-node majority and one wedged peer,
no leader existed after 15 seconds:

```
node n0: role=follower  term=2 voted_for=n1
node n1: role=candidate term=2 voted_for=n1
wedged peer absorbed 2 RequestVote/AppendEntries calls that never returned
```

The detail that matters: n1 had **already won**. It voted for itself and n0
granted its vote — a majority of 3. The election still never completes, because
the tally is blocked behind an RPC to a node whose vote is not needed. A wedged
peer is strictly worse than a crashed one here, and it is the more common
failure in a soft-realtime cluster.

**Smallest correct fix:** put a deadline on every RPC (well under the election
timeout), and resolve elections on the first majority rather than waiting for all
peers — `asyncio.wait(..., return_when=...)` with early exit, or count votes as
they arrive.

### 5. A hard crash destroys the replica's log ~58% of the time — CRITICAL
`src/raft/storage/filesystem.py:27-31`, `:40-44` · `probe_06_crash_during_log_write.py`

`_write_log()` and `store_metadata()` open the destination with mode `"wb"`,
which **truncates the real file in place**, and only then serialise into it.
There is no write-to-temp + fsync + atomic rename, and no directory fsync. The
`os.fsync` calls make writes durable but not atomic — different properties, and
only the second protects against a torn write. Any crash between the open and
the fsync leaves a partial pickle.

12 processes killed with SIGKILL while appending:

```
restarted cleanly:   5
log.pkl unreadable:  7      example -> EOFError: Ran out of input
meta.pkl unreadable: 0
```

Seven of twelve replicas were unrecoverable — `FsLogStorage` raises on
construction, so the node cannot start at all. `meta.pkl` survived in this run
only because it is small enough to land in one write; it is written by the same
unsafe pattern, and losing it is worse than losing the log — it holds
`current_term` and `voted_for`, so a node that loses them can vote twice in one
term and elect two leaders.

**Smallest correct fix:** write to `<name>.tmp`, `fsync` it, `os.replace()` onto
the target, then `fsync` the containing directory. Also checksum each record so a
torn tail is detected and truncated rather than failing the whole load.

### 6. Even-sized clusters commit on a minority — CRITICAL
`src/raft/core/logic.py:233-237` · `probe_02_commit_quorum_even_cluster.py`

`maybe_advance_commit_index()` sorts the match indexes of all N members and takes
`match_indexes[len // 2]`. For odd N that is the majority position; for **even N
it is off by one**. With N=4 it selects the index held by only 2 nodes when a
majority is 3. With N=2 the leader commits entirely alone.

```
stopped 2 of 4 followers; at most 2 of 4 nodes can hold a new entry
leader commit_index: 0 -> 1
  node n0: holds index 1? False
  node n1: holds index 1? True
  node n2: holds index 1? False
  node n3: holds index 1? True
2 of 4 nodes hold index 1; majority is 3
```

This breaks Leader Completeness. The three nodes that lack the entry (n0, n2 and
either stopped node) form a legitimate quorum, elect a leader that has never seen
index 1, and overwrite it — destroying an entry the cluster already reported as
committed. Note that the *election* quorum at `logic.py:116` is correct, so this
is not caught by any election test.

**Smallest correct fix:** `match_indexes.sort(); majority_match =
match_indexes[len(match_indexes) - (len(match_indexes) // 2 + 1)]`, i.e. index
`N - majority`. Correct for both parities.

### 7. A duplicated AppendEntries deletes committed entries — CRITICAL
`src/raft/core/logic.py:73-80` · `probe_03_stale_append_truncates_committed.py`

Raft §5.3 deletes existing entries only when they **conflict** — same index,
different term. `handle_append_entries()` instead calls
`truncate_suffix(first_new_index - 1)` unconditionally whenever the request
carries any entries, so an older, shorter batch deletes everything after it,
committed or not.

This requires no attacker. `broadcast_append_entries()` is invoked both by the
heartbeat loop and by `client_write()` **with no mutual exclusion anywhere in the
codebase** (there is not a single lock in `src/`), and gRPC gives no ordering
guarantee between two in-flight calls. A duplicated or reordered retransmission
is an ordinary network event.

Replaying one AppendEntries the leader had genuinely already sent:

```
follower n1 before: commit_index=3 log indices=[1, 2, 3]
replaying an earlier AppendEntries (term=1, prev_log_index=1, entries=[index 2])
follower response: success=True match_index=2
follower log after: indices=[1, 2]   (commit_index is still 3)
```

The follower now claims `commit_index=3` while its log ends at index 2 — it has
"committed" an entry it no longer holds. That is a corrupt, self-inconsistent
state, and if this node is elected it serves a log missing a committed entry.

Note the first version of this probe **passed**: the live leader re-replicated
the truncated entry within one 50 ms heartbeat and hid the damage. That masking
is precisely why the existing suite never caught it. Stopping the leader first —
modelling a crash with an RPC still in flight — removes the repair path and makes
the damage durable.

**Smallest correct fix:** walk the incoming entries against the local log; find
the first index where the terms differ; truncate only from there; append only the
remainder. If no entry conflicts, append nothing and return success.

### 8. ClientWrite reports success for writes that were never committed — HIGH
`src/raft/core/logic.py:249-257` · `probe_04_client_write_acks_uncommitted.py`

`client_write()` appends the entry, broadcasts once, and returns
`accepted=True` regardless of whether a quorum acknowledged it. `accepted` is
the only success signal the RPC gives a caller, so a client is told its write is
durable when a single un-replicated copy exists on one node — a copy the next
leader is entitled to overwrite.

```
stopped both followers; leader n2 is alone and cannot reach a quorum of 2/3
ClientWrite -> accepted=True index=1 term=1
leader commit_index 0 -> 0; entry index 1 committed? False
leader is still role=leader despite having lost quorum
```

The second defect visible there: **the leader never steps down on quorum loss**.
It stays leader indefinitely, continuing to accept and acknowledge writes it
cannot commit. Combined with Finding 2, `accepted=True` carries no information at
all about whether a command was committed or applied.

**Smallest correct fix:** hold the client request until the entry's index is
committed (future/condition resolved by `maybe_advance_commit_index`), with a
timeout that returns a definite failure. Separately, step down to follower after
an election timeout with no successful quorum contact.

### 9. A follower more than 4 MiB behind can never catch up — HIGH
`src/raft/core/logic.py:165`, `:201-202` · `probe_08_unbounded_append_batch.py`

`read_entries(progress.next_index)` is called with no end bound, so a lagging
follower is sent its entire backlog in one AppendEntries message. gRPC's default
receive limit is 4 MiB, so past that threshold every attempt fails with
RESOURCE_EXHAUSTED. The broad `except Exception` at `:201` only logs it,
`next_index` never advances, and the leader retries the same oversized message
forever.

```
stopped follower n1; it missed 48 entries of 128 KiB (~6.0 MiB backlog)
leader log reaches index 48; healthy follower n2 at commit_index=47
restarted n1; waiting 20s to catch up
after 20s the restarted follower's log reaches index 0 of 48 (commit_index=0)
```

Permanently wedged. The cluster runs at reduced redundancy indefinitely and no
client ever sees an error. `send_snapshot()` has the same unbounded shape — the
whole snapshot goes in one message — so the snapshot fallback fails for exactly
the large states that need it.

**Smallest correct fix:** cap entries per AppendEntries (count and bytes) and let
`next_index` advance incrementally; chunk `InstallSnapshot`. Do not let a broad
`except` swallow a permanent error — distinguish retryable from fatal.

### 10. Latency grows with log size and nothing ever compacts — HIGH
`src/raft/storage/filesystem.py:23-49`, `src/raft/core/state.py:106` · `probe_10_write_latency_scaling.py`

`FsLogStorage` keeps the whole log in one pickle file, rewrites **all** of it on
every append, and unpickles **all** of it on every read — and `read_entries`,
`first_index`, `last_index_term` and `compaction_base` are each called several
times per heartbeat per peer. One client write costs O(log size); total cost is
quadratic in writes.

```
callers of maybe_snapshot() in src/: 0
log ~  100 entries: median write   1.04 ms, worst  2.26 ms
log ~  500 entries: median write   1.98 ms, worst  2.25 ms
log ~ 1000 entries: median write   3.30 ms, worst  3.46 ms
log ~ 2000 entries: median write   6.06 ms, worst 11.42 ms
log ~ 4000 entries: median write  10.60 ms, worst 15.88 ms
median latency grew 10.2x between 100 and 4000 entries
```

Clean linear growth, and **`maybe_snapshot()` has zero callers in `src/`** — it is
reachable only from tests. Nothing ever compacts, so the log grows without bound
for the life of the cluster and this cost only rises. Extrapolating, 100k entries
puts a single write in the hundreds of milliseconds.

Two aggravators for a soft-realtime deployment. All this file I/O, including
every `os.fsync`, runs **synchronously on the asyncio event loop** — while a write
serialises, the node can neither send nor answer heartbeats, so replication
stalls in lockstep with disk latency and slow disks manufacture spurious
elections. And `apply_entries()` calls `persist_metadata()` (an fsync) on every
invocation even when nothing was applied.

**Smallest correct fix:** append-only segmented log with an in-memory index, so
appends are O(1) and reads are seeks; run storage I/O in a thread executor;
and actually call `maybe_snapshot()` from the node loop using the
`Snapshotting` config that is currently defined and never used.

### 11. The README advertises capabilities that do not exist — MEDIUM
`README.md:9`, `src/raft/node/service.py:32-34` · `probe_11_documented_capabilities.py`

```
ChangeMembership(add n2) -> accepted=False message='not implemented'
RPCs exposed: AppendEntries, ChangeMembership, ClientWrite, InstallSnapshot, RequestVote
```

README lists "Joint consensus membership changes" as a feature; the RPC is a stub
that always refuses, and `peers` is a fixed list passed at construction. There is
**no way to change cluster membership at all** — a node cannot be replaced without
restarting the whole cluster with new config.

Separately, there is **no read path**. No RPC returns committed state.
`KeyValueStateMachine.apply()` computes a return value for a `get` op, but
`apply_entries()` discards every return value, so even a read submitted through
the log could not be answered. A consensus service that cannot be read from is
not usable as one.

`README.md:3` calls the project "Production-grade"; `pyproject.toml:6` repeats it.
Given findings 1–10, that line should be removed before anyone deploys against it.

## SUSPECTED findings — reasoned from code, NOT reproduced

I did not build probes for these. They are ranked below the confirmed set
deliberately; treat them as leads, not results.

- **`InstallSnapshot` accepts stale snapshots** (`logic.py:91-107`). No check that
  `last_included_index` exceeds the current `commit_index`/`last_applied`. A
  delayed snapshot overwrites the state machine with older state via `sm_restore`,
  while `last_applied` is held at `max(...)` and never regresses — so the node
  never replays the difference and diverges permanently. `compact_prefix` also
  retains entries above `last_included_index` without checking them for conflict;
  Raft requires discarding the whole log when the existing entry at that index
  disagrees.
- **Snapshot metadata does not describe the snapshot contents**
  (`state.py:106-128`). The blob is `sm_snapshot()` — state as of `last_applied` —
  but it is labelled `last_included_index = min(last_applied, last_index -
  trailing)`. When those differ, restoring re-applies entries already baked into
  the blob. Harmless for idempotent `put`, corrupting for any non-idempotent
  command (counters, balances, append).
- **No no-op entry on leader election** (`logic.py:156-163`, `:243-245`). The
  commit rule correctly refuses to commit entries from an older term, but nothing
  appends a current-term no-op, so entries carried over from a previous leader
  stay uncommitted until unrelated client traffic arrives.
- **No PreVote and no leader stickiness** (`logic.py:19-39`). A node returning
  from a partition raises its term and forces a healthy leader to step down —
  avoidable unavailability, which matters more in soft-realtime than elsewhere.
- **No concurrency control at all.** There is not one lock in `src/`.
  `broadcast_append_entries` runs concurrently from the heartbeat loop and
  `client_write`, mutating the shared `progress` dict and `commit_index` across
  await points. Finding 7 is one observable consequence; there are likely others.
- **Commit can stall after compaction** (`logic.py:243-245`).
  `maybe_advance_commit_index` reads the entry at `majority_match` and silently
  returns if it is missing — which is exactly what happens once that index has
  been compacted away.
- **Election timer polls at 100 Hz** (`service.py:81-84`), and `_run_election_timer`
  awaits `maybe_start_election()` inline, so the stall in Finding 4 also stops the
  timer itself.

## Closing statement

**What was exercised.** Eleven claims were driven against live nodes through the
real gRPC service — `ClientWrite`, `AppendEntries`, `ChangeMembership` — in
single-node, 3-node and 4-node configurations, on loopback with real filesystem
storage. This covered: leader election with a healthy majority and with one
wedged peer; write, replication and commit; clean restart with a populated data
directory; SIGKILL of 12 processes mid-write followed by restart; a follower
stopped, left ~6 MiB behind and restarted; a malformed command applied across
three nodes; an unauthenticated payload from a client presenting no credentials;
and write latency sampled at five log sizes from 100 to 4,000 entries. The
existing suite was run as a baseline (134 passed, 96.45% coverage). Every
reproduction is a probe in `audit/evaluations/`, re-runnable via `run_all.sh`.
Finding 1's probe was additionally shown to report PASS once the defect was
patched, so the harness is known to discriminate rather than merely being red.

**What was not tested at all.** No sustained load and no concurrency beyond a
handful of in-flight requests — every probe is essentially single-client, so the
lock-free concurrent-mutation hazards behind Finding 7 were demonstrated only via
a replayed RPC, never by racing two real writers. Nothing in the snapshot
lifecycle was exercised end to end, because nothing calls `maybe_snapshot()`; all
snapshot-related findings are SUSPECTED. No network partition or asymmetric
partition (only stopped and wedged peers), no packet loss, no clock skew, no disk
exhaustion, no memory pressure. No multi-hour soak, so unbounded log growth is
extrapolated from a 4,000-entry measurement rather than observed at production
scale. No test crossed a real host boundary: everything ran on loopback, so real
network latency, TLS handshakes and gRPC keepalive behaviour are untouched. There
is no deployed `consensus.rodmena.co.uk` in this repo, so nothing was verified
against a served artifact — all findings are about the library as it stands at
`516441b`.

**What I remain unsure about.** Whether Finding 7 fires in normal operation
without a duplicated packet — I proved the truncation is reachable and durable,
but not how often the leader's own unsynchronised concurrent broadcasts actually
produce it; that needs a racing-writer probe I did not build. Whether the
`meta.pkl` write in Finding 5 is genuinely safer than `log.pkl` or merely small
enough to have got lucky in 12 trials — I believe it is luck, since the code path
is identical, but 0/12 is not evidence of safety. The true production latency
curve in Finding 10, since I measured to 4,000 entries on one machine's page
cache and a real deployment differs in both directions. And the SUSPECTED
snapshot findings generally: I read that code carefully and could not exercise
it, which is the least trustworthy combination in this report.

I am not describing this codebase as production ready, and on the evidence above
it should not carry traffic for `consensus.rodmena.co.uk` in its current state.
Findings 1, 2, 3 and 6 each independently cause silent, unrecoverable loss or
corruption of customer data; findings 4 and 5 each independently cause total loss
of availability or of a replica.
